# 0.2.0 — 并行批量解析

- 状态：已发布至 GitHub
- 日期：2026-10-11
- 目标：在保留可审计产物的前提下，让多个文件安全地同时解析。

## 新功能

- `document-parser batch --workers N` 指定文件级并发数，默认 2；Python `parse_directory(..., workers=N)` 同步支持。设为 1 可串行运行。
- 执行器限制同时排队的任务数量，避免一次提交整个目录。
- 每个批次写入独立的 `batches/<batch_id>/batch_report.json`，并在每份文件完成时追加 `results.jsonl`。最终报告保留输入路径排序。
- 每个解析运行目录追加随机 ID，避免同名文件在同一秒启动时互相覆盖。

## 修复

- OCR 审核任务创建和公共队列刷新加入跨进程文件锁，队列 CSV 先写临时文件再原子替换，避免并发批量解析时丢失记录或被读到半写入内容；决策及 OCR 结果追加也使用同一锁。
- 单文件解析失败时，在该运行目录的 Manifest 记录失败状态、错误类型、错误消息和最后完成的阶段；批次报告保留该目录路径。
- 并行 worker 各自创建 Pipeline；百度 OCR Provider 为每个 worker 创建独立 HTTP Session。

## 兼容性

- `ParsedDocument` Schema 仍为 `1.0`，解析结果字段没有更改。
- 批次报告路径从输出根目录的固定文件，改为每批独立目录；调用方应使用返回值中的 `report_path`。
- `pipeline.parse()` 在已创建运行目录后的错误会抛出 `ParseExecutionError`，原始错误保留在 `__cause__` 中。
- 启用自动 OCR 并并行批量解析时，自定义 OCR Provider 需实现 `clone()`；串行运行不需要。

## 验证

- 已有 22 个测试保持通过。
- 新增并行重叠执行、同名文件隔离、失败 Manifest、独立批次报告和 OCR 审核队列完整性测试。

## 已知限制与下一步

- 当前使用线程执行文件级任务，CPU 密集型 PDF 的实际加速需结合真实文档测量；后续可引入进程池。
- OCR 审核队列每新增任务会重新生成 CSV，大规模审核任务的性能仍需优化。
- 断点续跑、内容哈希去重和 XLSX 多表区域识别未纳入本版本。
